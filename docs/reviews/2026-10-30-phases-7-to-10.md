# Review: phases 7 to 10 and dev server

Date: 2026-10-30. Reviewer: Codex (`gpt-6.1-sol`, `codex exec -s read-only`),
scope `ec53529..5dfa040` (19 commits, 149 files): dedicated execution channel
for jobs, browser bay, ADR 0016 and 0017, core in `packages/host`, server
without UI, bridge desktop ↔ server with SSH tunnel, dev server in Docker.

Every finding was checked against the code before it was accepted.
Result: 11 findings (1 high, 9 medium, 1 low), all confirmed and fixed, each
with a test that was red before the fix. In addition there were two findings
from the real run in the dev server (No. 12 and 13).

Codex's verdict: the concept holds (shared core, desktop as transport,
separate partitions). The biggest risk lay at the lifecycle boundaries:
unchecked inputs at the bridge, and work and permissions that outlived a
cancellation or the removal of a bay.

| 18  | Permanent SSH errors (no `ssh`, host key) are retried without end                                     | Deliberately so: fixable while the app runs; pause at most 30 s. Justified in ADR 0019                                                    | –                                                                                     |

Check of the improvements (Codex, static): `RemoteCommand=none`,
`ControlMaster=no` and `ControlPath=none` complete and valid from OpenSSH 8.1
(Windows too). Two findings, low, both confirmed and fixed: the comment in
`tunnel.ts` and ADR 0019 promised a visible failure with `StdinNull yes`; with
an open forwarding, however, ssh can keep running – text corrected. And
`open-tunnel.mjs` swallowed connection errors, the test would have hung until
the timeout; now it aborts. Not adopted: the crash test only checks the local
port, not the target – for the question whether the tunnel ends with the app,
that is enough.
