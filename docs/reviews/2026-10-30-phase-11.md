## 11b – Permission dialog over the bridge

A permissions change, therefore adversarial and in two rounds. Every finding
fixed with a test that was red before, except where noted otherwise.

| No. | Round | Severity | Finding                                                                               | Fix                                                                                                                | Test                                                        |
| --- | ----- | -------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| 3   | 1     | medium   | A paired server could open any number of dialogs at the same time                     | One question after the other per connection, at most 10 open, duplicate IDs discarded; dialog closes on disconnect | `client.test.ts` "asks one at a time …", `prompter.test.ts` |
| 4   | 1     | medium   | "Last paired" was wrong: an older desktop that reconnects is asked                    | Not a behavior bug (both desktops are authorized); description corrected: last connected                           | –                                                           |
| 5   | 1     | medium   | A question right after `auth` was lost because the answer was not set up yet          | Questions wait until the answer is set up                                                                          | `client.test.ts` "… also right after auth …"                |
| 6   | 2     | high     | A question without a valid ID bypassed order and limit                                | The desktop checks ID and shape of the question                                                                    | `client.test.ts` "ignores malformed questions …"            |
| 7   | 2     | medium   | An answered ID could ask again                                                        | Answered and withdrawn IDs are blocked                                                                             | as No. 6                                                    |
| 8   | 2     | medium   | After the server's timeout the dialog stayed open and held up all following questions | The server sends `withdraw`; the desktop closes the dialog or removes the waiting question                         | `bridge.test.ts` "withdraws a question …", `client.test.ts` |
| 9   | 2     | medium   | The server held any number of open questions with timers                              | At most 10 open questions; further ones fail immediately, without storing                                          | `bridge.test.ts` "… takes at most 10 open ones"             |

Third round over the fixes: five complete, one new finding (medium): the guard
against repetition remembered every ID, also from invented `withdraw`
messages, and grew without limit. Fixed (red before): the desktop only accepts
rising IDs (the server counts up) and remembers only the last one; `withdraw`
only acts on shown or waiting questions. Known limit: a dialog that does not
react to `signal` would hold up the following questions; the Electron dialog
closes on `abort`.

No finding: unpaired or other connections cannot answer a question; answers
after the timeout and repetitions stay without effect; timeout and disconnect
store nothing, an explicit "Deny" does. Unchecked: display of control and bidi
characters from `bayId`/`target` in the native dialog; under macOS `signal`
does not close a dialog without a parent window (Electron 45), Hangar passes
the main window.

Fourth round (only the rising IDs): the first run hung for over 50 minutes
without output and was aborted; the check ran in the joint run with the fixes
for 11d (result below).

this).
