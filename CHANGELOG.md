## [Unreleased]

### Added

- Workspaces without a keychain (Linux without Secret Service, the server): with `HANGAR_KEY_PASSPHRASE` set, new relay keys are stored encrypted with it (`pass:`, scrypt + AES-256-GCM) instead of plain; existing `plain:` keys are still read. App and server drop the variable from their environment, so session shells and jobs do not inherit it. This is no isolation: on Linux a process of the same user can still read Hangar's original environment in `/proc/<pid>/environ`, and the key file is readable to the same user anyway; the passphrase protects keys at rest (backups, a copied disk), not against agents running as the same user.
- Agent bay: the footer with the usage limits also shows the weekly limit of Claude and Codex, if they report one: "7d", share free and the reset with date and time.
- License: MIT (`LICENSE`), copyright Derivo; also in `package.json` and the app's copyright.
- Browser bay: the page zoom of the selected tab shows next to the address ("110 %") once it is not 100 %; a click sets it back. Cmd/Ctrl +, - and 0 in the page change it. Bays get `zoom` in `BrowserTab` and `ctx.browser.resetZoom(id)`.
- Agent bay: context menu on sessions in the project tree (right click, Shift+F10 or the context menu key), also on the status lights of the collapsed sidebar. It combines change description, color, move up and down, open in its own window or dock, schedule job, environment variables, copy path, restart shell and close session. Arrow keys, Home and End select, Enter runs, Esc closes.
- Board over workspaces (ADR 0037, addendum): agents of other instances work on the board of a project shared in workspaces. They name the project in `project`; the workspace must share the `task.*` functions. Their tasks belong to the instance and do not become open again on their own. `dev.hangar.agents/project.list` now returns `shared`.
- Agent bay: sort sessions in the project tree. A session can be dragged onto another one of the same project and then takes its place; without dragging via "↑" and "↓" per session in the project overview. The order is in `state.json` and survives restarts.
- Sort the sidebar (ADR 0038): bays and shortcuts in the left sidebar can be reordered by drag and drop; without dragging via "Move up" and "Move down" in the context menu. The bays of the local server sort in between those of the app. The order is in `settings.json` and survives restarts.
- Password bay (ADR 0021): the new bay "Passwords" holds passwords and tokens, encrypted with the system keychain (`vault.json`, 0600); the UI never shows a value, only name, description and change. Environment variables of project and session refer to them with `NAME=@secret:PASSWORD`; the shell gets the value at start, only the reference is on disk. Below the field it says which passwords exist. If a password is missing or Hangar is closed (agent bay in the local server), the shell does not start and says why in the terminal. Reading the value is sensitive: Hangar asks the first time.
- Board bay (ADR 0037): tasks per project of the agent bay in three columns (open, in progress, done). The person creates, completes, reopens and deletes tasks; agents list, create, claim, note and complete them via the MCP tools `dev.hangar.board/task.*`. When a session ends, its tasks in progress go back to open. With a local server the board runs there with the agent bay.
- Manifest: functions with `bayOnly` are called only by bays; the bus rejects agents and other instances before any rule, MCP does not list them. New host module `secrets` (`ctx.secrets.encrypt`/`decrypt`). The agent bay offers bays `session.info` and `project.list`.
- Local server, step 5 (ADR 0036, item 11): with a local server the agent bay shares projects in workspaces again and accepts handovers. The workspaces move into the server together with their identity, your Hangar keeps its fingerprint; "Settings → Workspaces" controls them there. If you had already set up workspaces in the app, the first start afterwards stops the local server once; running shells end in the process. The bridge speaks protocol version 4: an older server rejects the new app until it has been restarted.
- Local server, step 4b (ADR 0036): on macOS the agents in the installed app now run in the local server by default. On the first start after the update the agent bay moves once; running shells of the app end once in the process. "Settings → Local server" turns this off or on for the next start, with "Restart Hangar". Turning it off asks first, stops the server and brings the agent bay with projects, sessions, jobs, permissions and settings back into the app; runtime copies and LaunchAgent are removed. `HANGAR_LOCAL_SERVER=0` or `1` overrides the setting. A build from the repository starts the server only on request.
- Local server, step 4a (ADR 0036, still only with `HANGAR_LOCAL_SERVER=1` on macOS): the bays of the local server are in the sidebar under their name, without a server entry of their own; their notifications no longer carry a server name. If the server is not running, "Agents" stays in the sidebar and shows "Local server is not running" with the error, "Restart" and "Open log". If an older version than the installed app runs in the server, "New version ready" with "Restart local server" appears above the bay; if shells are running, Hangar asks first, because they end. The tray menu shows how many shells run in the server and restarts it. New server message `sessions` (without a new protocol version).
- Local server, step 3 (ADR 0036, still only with `HANGAR_LOCAL_SERVER=1` on macOS): agents in the local server reach the bays that run only in the app, such as the browser. The app offers their functions only to the local server; the server checks permissions as before, the app checks them once more under the subject `local-server:<bay-id>` and gives each session its own browser tabs, which end with the session. If the app is closed, a call fails with "Hangar is not open"; the tools stay listed. Rules for agents on bays of the app move along on the move. For this the bridge speaks protocol version 3: an older server rejects the new app until it has been restarted.
- Local server, step 2 (ADR 0036, still only with `HANGAR_LOCAL_SERVER=1` on macOS): the agent bay now runs only in the local server. On the first start Hangar moves its data, its jobs, the permissions on its functions and its settings into the server once (marker `<userData>/local-server/migrated`); its shells keep running afterwards when Hangar quits, is killed or is replaced by a new bundle. "Add project" shows the Mac's folder dialog. The UI of the bay comes from the runtime copy, so in the version of the server. Shells and jobs no longer inherit `ELECTRON_RUN_AS_NODE`.
- Local server, step 1 (ADR 0036, for now only with `HANGAR_LOCAL_SERVER=1` on macOS): Hangar starts `hangar-server` as a LaunchAgent from its own copy of the app per version (`<userData>/local-server/runtime/<version>`) and pairs with it without entering a code. The server keeps running when Hangar quits. The agent bay still stays in the app. The server now binds its port before the bays start, reuses the port of the last start and writes port and fingerprint to `<data>/listen.json`, every pairing code to `<data>/pair-code` (both 0600); new option `--cli`.
- Agent bay: sort and collapse projects in the project tree. A project can be dragged onto another one and then takes its place; without dragging it works via "Move project up" and "Move project down" in the project overview (WCAG 2.5.7). The order is in `state.json`. A project with sessions collapses via "▾" before its name: path and sessions disappear, if a hidden session waits for input, its light stays on the project. The state survives restarts.
- Agent bay: status "waiting on background" (ADR 0035). If the answer of Claude Code ends while a background task is running (for example waiting for CI), the session no longer shows "done" but "waiting on background" (dashed ring); when the agent continues, "working" again. No notification, no badge. `hangar status done --hook` reads the input of the stop hook for this. Applies from the next shell start of a session.
- Install, update and roll back bays (ADR 0034, Phase 20): "Settings → Install bays" lists the bays of the index (`HANGAR_BAY_INDEX`, key `HANGAR_BAY_INDEX_KEY`). Install and update show beforehand what the version is newly allowed to do (functions, `uses`, agent sessions, capabilities, newly sensitive functions) and take effect from the next start; new bays go into the sidebar. If the data format changes, Hangar backs up the data; "Roll back" restores the previous version together with this backup.
- `.bay` packages (ADR 0033, Phase 19): `pnpm pack:bay <id>` packs `manifest.json`, icon and `dist/` of a bay reproducibly as tar.gz and signs it with Ed25519 (`--keygen` creates the key). `@hangar/host` checks checksum and signature (`verifyPackage`), unpacks only files and folders inside the target (`unpackBay`: no links, no `..`, no absolute paths, nothing twice) and checks a signed index with an expiry date and a version counter (`verifyIndex`).
- Manifest permissions (ADR 0032, Phase 18): new fields `uses` (functions of other bays that the main part calls), `agentSessions` (only then does `registerAgentSession` issue session tokens) and `dataVersion`. `ctx.call` rejects targets of other bays that are not in `uses`. The agent bay declares `agentSessions: true`.
- Handovers between agents (ADR 0031, Phase 17): `dev.hangar.agents/handover.create` opens a new session with its own worktree, locally on the named branch, and shows "Handover from …" above its terminal with task, branch and context. The agent in it reads it with `hangar handover` or `handover.get`; `hangar handover create "<task>"` hands over from the shell. Other instances hand over only into shared projects, only with sharing in the workspace and only text and Git references (at most five open). Never input into a running shell.
- Workspaces in the UI (ADR 0030, Phase 16): under "Settings → Workspaces" Hangar connects to a relay (`wss://`), creates workspaces (operator token), invites (workspace, invitation token and own fingerprint to pass on) and joins (with the fingerprint of the inviter). Whoever invited then sees "wants to join" with the fingerprint of the new instance and admits or rejects it; members can be removed, functions shared per workspace. The agent bay shares sessions of a project only with "Share in workspaces" (default off) and shows under "Other instances" project, session, description and status of other instances with their origin, read-only. The instance's private keys are stored encrypted with the system keychain. New in the SDK: `ctx.workspaces` (`publish`, `states`, `onState`) with `hostModules: ["workspaces"]`.
- Hangar relay (ADR 0011, Phase 15): the new program `apps/relay` (`@hangar/relay-server`) forwards end-to-end encrypted envelopes between Hangar instances over WebSocket with TLS (without TLS only loopback). Sign-in by signature over a challenge, workspaces only with the operator token (`HANGAR_RELAY_TOKEN`), invitations single-use and valid for seven days, member lists checked by the same rules as the instances. The relay stores no contents and writes none to the log. `@hangar/relay` gets the protocol and `RelayClient`: remote functions appear in the bus as `remote.<name>-<fingerprint>.<bay-id>/<function>`, calls from the workspace are checked by the bus against membership and share list. The sign-in at the relay is bound to its address (`HANGAR_RELAY_URL`). Image `pnpm image:relay` with a Compose example; guide `docs/relay-operations.md`; `pnpm test:container` also checks the relay image.
- New package `@hangar/relay` (ADR 0011, Phase 14): identity per instance (Ed25519, X25519, self-signed document, fingerprint SHA-256), signed and versioned member list per workspace (only members sign new versions, revocations stay, valid at most seven days), envelope with XChaCha20-Poly1305 and a key per direction (HKDF-SHA256), header as authenticated data, Ed25519 signature, protection against replay with epoch and number, written to disk before execution. Still without a network. New dependency `@noble/ciphers` (XChaCha20-Poly1305 is missing in `node:crypto`).
- Bus: callers from other Hangar instances (ADR 0011, Phase 13). New kind `remote` with the fingerprint of the instance and workspace; the rule "own bay" never applies to them. Before every call the bus checks membership, share list, `remote: true` and "not sensitive", only then the stored permission (subject `remote:<fingerprint>/<bay-id>`). Manifest: field `remote` per function, bay ids with `remote.` are rejected. The permission dialog names instance and workspace. Still without a network: the relay follows in Phase 14 and 15.
- Hangar server in operation (ADR 0029): production image (`pnpm image:server`, `docker/server/Dockerfile`) without root, with a health check and volumes `/data` and `/projects`; examples for Docker Compose (`restart: always`, only the machine's loopback) and systemd (`Restart=always`). Guide in `docs/server-operations.md`: setup, pairing, deploy keys per repository, API keys as environment variables, backup of the data folder, restart and update. `pnpm test:container` checks the image with Docker up to the restored session after `docker restart`; in CI as a job on Ubuntu.
- Sidebar: shortcuts to programs, folders, files and web pages (ADR 0027). The plus is now called "Add to sidebar" and offers, besides the bays, "File or program …", "Folder …" and a field for a web page (only `http://`/`https://`). Click opens the target with the system, right click removes it. The shortcuts are under the bays with the system's icon or a globe and stay in `settings.json` (`shortcuts`).
- Agent bay: the project bar can be collapsed ("‹" at the top left). Collapsed it is as wide as the bay sidebar and shows only the status light per session; click opens the session, the tooltip names session and project. The fields get the space. The state survives restarts.
- Agent bay: if selecting copies text to the clipboard, the terminal briefly shows "Copied to the clipboard" (also for screen readers as `role="status"`).
- Agent bay: zsh prompt in sessions (ADR 0025). New sessions show folder and Git branch, for example `~/code/hangar (main) %`. Under "Bay settings" the prompt can be changed in zsh syntax (`${vcs_info_msg_0_}` is the branch); empty keeps the prompt of your own zsh. Hangar still loads all your own startup files for this (`.zshenv`, `.zprofile`, `.zshrc`, `.zlogin`). Bash and Windows stay unchanged. For this, bay settings know the type `text` besides yes/no; `ctx.settings.get` returns `boolean | string`.
- Agent bay: tabs in color. Every session can be marked in the header of its field via "Color" with one of eight colors (red, orange, yellow, green, teal, blue, violet, pink); the stripe is at the field and at the entry in the project tree, "None" removes it. The color survives restarts (`state.json`). All eight colors hold at least 4.5:1 against the surfaces, light and dark; new theme tokens `--hangar-color-tab-*`.
- Agent bay: whatever is selected with the mouse in the terminal of a session is in the clipboard after release. Can be turned off per session via "Selecting copies" in the header of its field; whether new sessions get it on or off is in the settings under "Bay settings".
- Agent bay: usage limits in the footer (ADR 0024). Below project tree and fields it shows how much of the 5-hour quota of Claude and Codex is free and when it resets. Hangar reads Codex from its logs in `~/.codex/sessions`; Claude Code reports it via `hangar statusline`, which Hangar enters as `statusLine` in every session and which then calls the person's own statusline with the same data. New: MCP tool `quota.report`, CLI command `hangar statusline`.
- Bay settings (ADR 0023): bays declare settings in the manifest (`settings`, so far only yes/no); the Hangar settings show them per bay, stored in `settings.json`. New in the SDK: `ctx.settings.get` and `ctx.settings.onChange`.
- Servers speak the language of the desktop: the desktop app sends its language when pairing and on every connect. The server takes that of the most recently connected desktop, also for notifications that arise while none is connected (it remembers them across a restart). Error messages about the path of a project thus come in German or English. `HANGAR_LOCALE` on the server sets the language. Notifications of a server name it in the title, for example "Homeserver: Session is waiting for input". New in the SDK: `ctx.onLocaleChange`.
- Jobs of a server in the settings: under "Jobs" there is a group of its own per connected server ("On the server …") next to "On this computer", with schedule, runs and result; pause, resume, "Run now" and delete take effect on the server. The list updates when a job runs there or a server comes and goes. For this the bridge speaks protocol version 2; an older server rejects a new desktop app with a clear message.
- Notifications and badges from servers: if a bay on a server reports something (such as a waiting session), the system notification appears on the connected desktop; click opens the server bay. The badge is at the server bay in the sidebar and also counts on the app icon. If no desktop is connected, the server collects the last 50 notifications and shows them on the next connect.
- Permission dialog over the bridge: if an agent on a server needs a permission, the server asks the connected desktop. The usual dialog names the server ("On the server …"), the answer applies and stays on the server. Without a connected desktop, without an answer within 5 minutes or on abort the call fails without a block being stored; rules in `permissions.json` still apply. The desktop shows questions of a server one after the other, at most 10 open, and closes the dialog when the connection ends.
- Agent bay on a server: "Add project" asks for the path on the server instead of opening a folder dialog. An empty path is rejected; a path outside the shared folders, without a Git repository or without a folder shows the server's message at the field. Enter adds, Escape cancels. New in the SDK: `window.hangar.server` names the server of a server bay.
- Bridge: if the connection to a server drops or an attempt fails, the desktop app reconnects by itself, after 1, 2, 4 … at most 30 seconds. A server with a different key or without a valid token is not tried again; disconnect ends the attempts. CI checks the bridge over real `ssh` against the dev server (`pnpm test:ssh`, Ubuntu).
- Dev server in Docker (ADR 0020): `pnpm dev:server` starts `hangar-server` with OpenSSH and the agent bay in a container (SSH only on `127.0.0.1:2299`), creates keys and ssh config in `.dev-server/` and names address, fingerprint and pairing code; the desktop app pairs with `HANGAR_SSH=.dev-server/ssh pnpm dev`. `pnpm test:ssh` checks the bridge with it over real `ssh`, up to the session of the agent bay in the container.
- Bridge desktop ↔ server, part 3 (ADR 0019): the address when pairing may now be `user@host:port`. Hangar then builds an SSH tunnel itself (`ssh -L`) to the port on which `hangar-server` listens there, also on every later connect; `127.0.0.1:port` still connects without SSH. SSH runs without prompts (`BatchMode`): key and host key must work in the terminal beforehand, otherwise Hangar shows the message of ssh. The pairing dialog sets the focus on the first field itself and can be operated entirely with the keyboard.
- Bridge desktop ↔ server, part 2 (ADR 0019): the plus in the sidebar offers "Connect to server". Enter name and address (loopback only, for example over an SSH tunnel), compare the fingerprint with the server's log, enter the pairing code. Afterwards the server appears as a group in the sidebar, with a status light and its bays, for example "Agents (Homeserver)"; their UI comes from the local bundle (same version required), calls and events go over the connection. Click on the server: disconnect, connect, remove server. Paired servers are in `servers.json` and reconnect on start.
- Bridge desktop ↔ server, part 1 (ADR 0019): the server accepts desktops over WebSocket at `/connect`. It identifies itself with an Ed25519 key (fingerprint in the log). A desktop pairs once with the code from the log and afterwards connects with a token; token and code go out only when the server has proven its key. New package `@hangar/bridge` with protocol and client. The display in the desktop app follows.
- Hangar server without a UI (ADR 0018): `hangar-server --data <folder>` loads bays, starts the MCP server and scheduler and runs jobs under Node, without a screen and without Electron. Permissions only from stored rules, without a rule it rejects. `GET /health` shows version, bays and jobs (without output); listens only on loopback. Projects come via a path that must lie under a shared root folder (`--root`), also after resolving symbolic links; for this `ctx.pickFolder` now takes `path`.
- Add and remove bays (ADR 0017): a new Hangar starts with an empty sidebar – at the top the Hangar mark (overview, selected), below it a plus. The plus opens a modal with all found bays that are not yet in the sidebar; the selection starts the bay and selects it. Right click on a bay → "Remove from sidebar" ends it together with windows, tabs and MCP tools, its data folder stays. Only bays in the sidebar run; the sidebar is in `settings.json` (`bays`).
- Browser bay (`dev.hangar.browser`, ADR 0015): web pages in tabs with address bar, back, forward, reload; the person's tabs are open again after a restart. Agents open their own tabs with their own cookies via MCP (`tab.open`, `tab.navigate`, `tab.list`, `tab.close`), read text, click, fill fields and save screenshots as PNG (`page.text`, `page.click`, `page.fill`, `page.screenshot`); the person sees their tabs with the label "Agent". New host module `browser` in the SDK: manifest `hostModules`, `ctx.browser`, `window.hangar.browser.show`.
- Functions "open to agents" (ADR 0016): with `openToAgents` in the manifest, agents of any bay call a non-sensitive function without asking; a block in the settings still applies. The browser functions are open, so agents no longer see eight permission dialogs. New event `ctx.onAgentSessionEnded`: when an agent session ends, the browser bay closes its tabs.
- Scheduler for jobs (ADR 0013): bays schedule jobs via `ctx.jobs` with a cron expression (five fields, local time) that run in the main process, even without a loaded bay UI; a missed run is made up once after waking. New package `@hangar/scheduler` without Electron. The settings show under "Jobs" all jobs with schedule, next and last run and result, with pause, resume, "Run now" and delete. Agent bay: "Schedule job" in a session types a command into its shell at the scheduled time and reports exit code and last output line; agents use `job.add` (sensitive) and `job.list` for this.
- Concept for Hangar on a server (`docs/concept-server.md`): permanently running jobs and agent sessions without a screen, shown in the desktop app.
- Concepts for Hangar relay (collaboration of several instances) and the bay registry with ADR 0011 and 0012 (proposed), checked by Codex against the code; all 20 findings are incorporated (`docs/reviews/2026-10-28-relay-registry.md`).
- Permissions in the settings reworked: per caller a table with function, description, "sensitive", sharing, time of granting and last call; session permissions carry the name of the session. The sharing can be changed directly, a permission revoked or, under "Set a rule", set before the first access. Filter by caller and search by function. Bus: `setMode`, `grantedAt`, `lastUsed`; SDK: `ctx.labelSessions`.
- Agent bay: sessions side by side in the grid. "Add field" divides the workspace; every terminal keeps at least 80 × 24 characters, the arrangement depends on the available space (on a 49-inch widescreen four and more side by side). If no more field fits, Hangar says why; a window that has become smaller scrolls instead of squashing. Fields and focus survive restarts (ADR 0010).
- "Undock" opens a session in its own window, "Dock" or closing the window brings it back. Undocked windows reopen after a restart. Bays can open their own windows for this: `window.hangar.windows` in the SDK.
- Switch for the color scheme above the gear in the sidebar: System, Light, Dark (click cycles through). Applies to shell, bays and terminal and survives restarts (`settings.json`, `theme`).
- Hangar overview: the Hangar mark at the top of the sidebar opens an overview with the Hangar version, the global Git identity (name, email; if a value is missing, the `git config --global` command is shown with it) and the loaded bays with id and version, plus bays that could not be loaded.
- Project overview in the agent bay: a click on project name or path in the tree shows the sessions of the project as a table (status, branch, ports, uncommitted files, commits that the main checkout does not have) with open, create and close; orphaned `hangar/*` branches of closed sessions with delete after confirmation; environment variables with which new sessions of the project start. "Remove project" is now there instead of as "×" in the tree.
- After a restart Hangar opens the window at the same place and in the same size (also maximized), with the most recently chosen bay or the settings and the most recently chosen session. If the saved position lies on no existing screen any more, the window opens at the default position.
- German and English (ADR 0009): default is the system language (German if preferred, otherwise English), switchable in the settings under "Language" from the next start. Bays receive the language as `ctx.locale` and `window.hangar.locale`, catalogs choose it with `catalogFor` from `@hangar/sdk/i18n`. The CLI follows `LC_ALL`/`LC_MESSAGES`/`LANG`. `HANGAR_LOCALE` forces a language, `en-XA` is a pseudo-locale for tests.
- `./start.sh`: checks Node.js and pnpm, installs if needed and starts `pnpm dev`.
- Packages with electron-builder for macOS (dmg, zip), Windows (NSIS) and Linux (AppImage); CI builds them on all three platforms, `release.yml` publishes tags on GitHub Releases.
- Auto-update via electron-updater with channel "Stable" or "Beta" in the settings.
- `pnpm create:bay <id>` creates a runnable bay; written-out skills under `.claude/skills/`.
- Documentation: README, `docs/architecture.md`, `docs/bay-development.md`, `docs/mcp.md`, API reference via `pnpm docs:api`.
- Status bar per session with the types `text`, `path`, `bar` and `badge`.
- System notification and badge (sidebar and app icon) when a session waits for input; click brings the bay to the front.

- Monorepo with pnpm workspaces, TypeScript (strict), ESLint, Prettier, Vitest with a coverage gate, lefthook and GitHub Actions for macOS, Windows and Linux.

### Changed

- `pnpm create:bay` adds the new bay to the bundled bays in `apps/desktop/electron-builder.yml`; it no longer has to be entered by hand.
- README: one-line pitch, screenshot (light and dark, rendered by `apps/desktop/e2e/readme-screenshots.spec.ts` with `HANGAR_SCREENSHOTS=1`), "Why", features with board, password bay and local server, status, "How it works" and "For AI agents". Sessions are described as shells in the project folder (ADR 0022), no longer in their own worktree.
- Agent bay: "Add project" stays at the top of the project tree and the session counts at the bottom; only the projects scroll between them. Keyboard focus scrolls clear of both.
- Board: a new task is created like a card in a list: "Add a task" at the end of the column "Open" opens a small form (title, optional description, Esc cancels), instead of a form across the page.

- Documentation in English (ADR 0039): README, `docs/` with ADRs and review records, every `CLAUDE.md`, `AGENTS.md`, the project skills and this changelog are translated; doc files have English names.

- Permissions between bays (ADR 0032, addendum): what a bay declares in `uses` and is not sensitive is called without a permission dialog; sensitive functions still ask, a block in the settings still applies.
- E2E tests open their windows invisibly, without a Dock icon and without focus; whoever works on the Mac is no longer disturbed. `HANGAR_E2E_SHOW=1` shows them again.
- `pnpm dev` uses a profile of its own, "Hangar Dev", instead of the profile of the built Hangar; a restart during development no longer ends working sessions. `HANGAR_USER_DATA` still takes precedence.
- New UI in black and orange (ADR 0026, draft `docs/mockups/hangar-minimal.html`): fine lines, no bevelled corners and no grid any more, dark mode a bit lighter. Orange glows only on the active item: focused field, selected session, active bay, usage and status bars. "Waiting" is yellow. UI in Geist Mono, headings in Michroma instead of Chakra Petch. Theme tokens `--hangar-cut` and `--hangar-color-grid` are dropped, new are `--hangar-glow` and `--hangar-color-dock-glow` (the sidebar stays dark in light mode too).
- Agent bay: every session gets 100 instead of 10 ports (`HANGAR_PORT_BASE` up to `+99`). Existing sessions keep their initial port; a new block skips blocks in which one of them lies.
- Agent bay: "New session" always starts the shell in the project folder instead of in a worktree of its own (ADR 0022); Hangar creates no branch and deletes nothing on closing. Several sessions of a project share the folder; without a description they are named after the first eight characters of their id, under "Branch" it says "Project folder". Existing worktree sessions keep running.
- Agent bay: undock and close session are icon buttons at the top right of the field header ("↗", "×"; in the own window "↙" for docking), the other buttons are below.

On Windows the job starts via `cmd.exe` or PowerShell. The output is now only in the settings under "Jobs".

### Fixed

- MCP server: the rate limit forgets buckets that are full again once it holds 1000, instead of keeping one per token ever used.
- Desktop: relay keys that `HANGAR_KEY_PASSPHRASE` cannot open (missing or wrong) no longer stop the start without a word; an error box names the reason and Hangar starts without workspaces, the encrypted identity untouched. The in-app relaunch keeps the passphrase.
- Agent bay: a job that timed out or was stopped now ends even when the kill misses a child that keeps its output open (a failed `taskkill` on Windows, a child outside the process group); after 2 s Hangar closes the pipes itself.
- Agent bay and server: git calls drop `GIT_*` variables in any case (`git_dir`, `Git_Config_Count`); Windows reads environment names case-insensitively, so they still reached git there.
- Server tunnels: `StdinNull yes` in the person's ssh config no longer ends the tunnel at once. The desktop reads `ssh -V` and passes `-o StdinNull=no` from OpenSSH 8.7 on; older versions, which reject the option, get the arguments as before.
- MCP server: each session token is rate limited (bursts of 100, 600 requests per minute, enough for the statusline's quota reports); beyond that the server answers HTTP 429 `Too many requests`. Other sessions are not affected.
- Agent bay: when 100 creations or removals of sessions and projects already wait, a new one is refused with "The agent bay is busy" instead of queueing without limit.
- Agent bay: its own git calls (worktrees, branches, state) run without any `GIT_*` variable of Hangar's environment, as the server already does; before, only the variables that redirect git to another repository were removed. Session shells keep them.
- `.bay` packages: `unpackBay` refuses paths with bytes outside printable ASCII. It read the header as ASCII and dropped the high bit, so `0xAE 0xAE` came out as `..`.
- `.bay` packages: `packBay` packs only bays whose id starts with `dev.hangar.`; an id such as `evil.com.hangar` is refused.
- Agent bay, Windows: a job that times out or whose session closes now ends the whole process tree of its command (`taskkill /T /F`), not only `cmd.exe`.
- Tests: the relay test "a function shared in two workspaces stays …" waits up to 5 s for the join instead of 1 s; on the Windows CI runner it failed now and then.
- Relay: an instance publishes its own member list changes one after another. A renewal at the same time as adding or removing a member no longer makes the relay refuse one of them with "Not newer than the stored list".
- Local server: while it restarts, the hint "New version ready" shows "Local server is starting …" instead of the button, also while the old server is still connected; before, nothing changed until it was down, so the restart looked like it did not start.
- Local server: a new build of the same version now reaches the server. The runtime copy is named `<version>+<build id>`; before, every build of 0.1.0 kept running the first copy, also after "Restart local server". The hint "New version ready" now also appears for a new build of the same version and names both builds.
- Agent bay: no more lost output when the app attaches to a running session again (after a restart of the app, with the local server or a server): output that arrived before the scrollback was dropped, although it could be newer than it.
- Agent bay: the Codex usage limit no longer disappears when the newest Codex log has no limit (for example of `codex exec`); the newest log that has one counts.
- Browser bay: no horizontal overflow at 200 % zoom in a narrow window (under 500 CSS pixels); the grid column no longer grows to the width of the tab strip.
- Linux package: the executable is called `hangar`; AppImage refused the default `@hangardesktop` from the package name.
- Windows: the relay state (replay counters, relay server) no longer fails with `EPERM`; Windows refuses fsync on a folder, so `writeDurable` flushes the renamed file there. Git's repository root (`C:/…`) is resolved to the platform's form, and adding a project compares it with the resolved form of stored paths, so an old `C:/…` entry still counts as a duplicate.
- E2E tests retry twice in CI; a test that only passes on retry is reported as flaky instead of failing the run (terminal waits on the slow runners).
- Tests run on the Linux and Windows CI runners: their own Git identity and `/bin/sh` instead of zsh, a real temporary folder (no 8.3 short name), no line ending conversion in test repositories; checks of POSIX file modes, shebang scripts, `SIGTERM` exit codes and an empty `PATH` are skipped under Windows.

- Handovers: if two projects carry the same name, `handover.create` with a project name rejects ("Project name is ambiguous") instead of taking the first one in the tree (the name of the own project still means the own one); the handover could otherwise land in the wrong project.
- Permissions: "Deny" in the settings now also blocks a session that had previously been allowed the function "For this session"; until now the block applied to it only after its end.
- Local server: if stopping the server fails when turning it off, the app no longer starts a second agent bay, even if the bay in the server had not yet written any data.
- Local server: if a session ends while the app is disconnected, its browser tabs close on the next connect (the server remembers up to 500 session ends).
- Local server: a call of an agent that waits in the permission dialog of the app no longer runs after a connection drop, even if it is approved afterwards.
- Local server: tray and confirmation prompt on restart count running shells instead of sessions; a shell ended with `exit` no longer counts. New in the SDK: `ctx.setRunning(count)`.
- The hint "New version ready" wraps at 200 % zoom instead of shortening its text with "…"; the bay moves down by its measured height.
- Server: an invalid WebSocket frame before sign-in ended `hangar-server`; anyone on the server's loopback could shoot it down this way. Now only the one connection closes.
- Tests clean up their temporary folders: Vitest and Playwright create a folder `hangar-test-run-*` per run, set it as `TMPDIR` and delete it at the end (`scripts/test-tmp.ts`). Until now repos, data folders and Chromium profiles of every run stayed behind, most recently almost 99,000 folders with 24 GB.
- macOS: a click into a Hangar window that is not active takes effect immediately, for example into the terminal, which then has the focus. Until now the first click only activated the window and a second one was needed (`acceptFirstMouse`).
- Agent bay: a link in the terminal (OSC 8, as Claude Code writes it) opens in the browser after the confirmation prompt; the prompt names the real target, not the visible text. Until now xterm opened nothing after "OK", because it requested an empty window that Hangar rejects.
- Agent bay: after a restart the history of sessions in which a full-screen program such as Claude Code ran was missing. When truncating to 500,000 characters Hangar looked for the next line start; such programs write hardly any line breaks, the next one was only in the restart notice, and everything before it was dropped. The search now goes at most 4096 characters far.
- Agent bay: "waiting for input" only when Claude Code needs an approval or a question. The "idle" hint (`idle_prompt`, about 60 s after an answer, also while waiting for CI in the background) no longer changes the status. Applies from the next shell start of a session.
- Folder selection (such as "Add project" in the agent bay) opens in front of the Hangar window instead of behind it: the dialog is attached to the focused window, otherwise to the main window.
- Agent bay: an API key in the environment of Hangar (such as `ANTHROPIC_API_KEY` of a server service) reaches sessions and jobs again. `ANTHROPIC_*`, `CLAUDE_*` and `MCP_*` are dropped only if Hangar itself runs in a Claude Code session (`CLAUDECODE` set).
- Multi-click on the same button (ADR 0028): a double or multiple click creates only one session, one field or one tab, runs a job once, deletes it once and opens a shortcut once. A bay that is chosen again on start does not start twice (until now a failed second start removed the functions of the first). Pairing a server does not open a second connection on repeated "Next" and does not pair twice; "Open" in the browser bay opens one tab, not several. A second delete, close or revoke no longer shows an error message; if revoke, set, back, forward or reload fails, the reason appears as a message instead of going unnoticed. Older answers on repeated "Refresh" of the project overview and the permissions no longer overwrite newer ones.

- Multi-click on send buttons (ADR 0028): a double click on "Add job" occasionally scheduled the job twice, "Open" in the browser bay opened two tabs, and the second click on "Next" when pairing a server ended up on "Pair" and reported a missing code.
- A bay that is removed from the sidebar during its start does not return after the start.
- Browser: if a second view took over a tab and the first one closed, the tab also disappeared from the second one. If the shown tab is closed in the main process before the bay knows about it, no unhandled error arises any more.

- Agent bay: "Schedule job" without a schedule (empty or only spaces) reports "Schedule is missing" instead of "Invalid schedule “”".

- Agent bay: a new session no longer gets a port range that reaches into that of an older session (sessions from before the blocks of 100 do not start on the grid).
- Agent bay: key presses in a terminal that has just been opened are no longer lost while its previous content is still being loaded.
- Agent bay: after a restart mouse coordinates such as "35;59;19M" appeared in the terminal. A program that had ended (such as Claude Code) had switched on mouse tracking, and the restored scrollback switched it on again in the new terminal. Before the new shell, mouse and focus reports are now switched off.
- Agent bay: "1;2c" appeared in the terminal without input. When replaying the scrollback (reload, undock) xterm.js answered old terminal queries again, and the answer went to the shell as input. Answers during replay are discarded.
- Bridge: if the desktop app crashed, its `ssh` tunnel kept running. ssh now ends with the app: the tunnel runs `cat` on the server on its standard input.
